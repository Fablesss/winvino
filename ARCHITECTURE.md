# Архитектура

Как фотография превращается в карточку вина и где проходят границы между слоями.
Запуск и переменные окружения — [README.md](README.md).

## Сервисы

```
браузер / Telegram
        │  multipart image
        ▼
┌───────────────┐   /api/*   ┌─────────────┐  POST /v1/recognize  ┌──────────────────┐
│ web (Next.js) │──────────► │ api (Hono)  │ ───────────────────► │ recognizer (Node)│
│ :3000         │            │ :8787       │ ◄─────────────────── │ :8080            │
└───────────────┘            └──────┬──────┘   топ-5 + сигналы    └────────┬─────────┘
┌───────────────┐  POST /v1/        │                                      │ JSON по строке
│ bot (Node)    │  recognitions     │ SELECT карточки                      ▼
└───────────────┘───────────────────┤                          ┌───────────┴──────────┐
                                    ▼                          │ visual worker (torch)│
                             ┌─────────────┐                   │ ocr worker (paddle)  │
                             │  Postgres   │                   └──────────────────────┘
                             └─────────────┘                    индекс + каталог из artifacts/
```

| Слой | Пакет | Чем занят | Чего не знает |
|---|---|---|---|
| Клиенты | `platform/web`, `platform/bot` | съёмка, сжатие, показ карточки | как устроено распознавание |
| API | `platform/api` | контракт, валидация фото, **решение** matched/ambiguous/not_found, карточки из базы | как считаются признаки |
| Распознаватель | `scripts/serve-recognizer.mjs`, `scripts/lib/` | признаки, поиск, слияние сигналов | что такое «карточка вина» и откуда она берётся |
| Модели | `ml/`, `ocr/` | эмбеддинги и текст | HTTP, каталог, база |
| Контракт | `platform/contract` | zod-схемы, коды ошибок, OpenAPI, fetch-клиент | всё остальное |

Ключевое разделение: **распознаватель отдаёт сигналы, решение принимает API.** Распознаватель
возвращает топ-5 слагов с уверенностью, абсолютное визуальное сходство лучшего референса и
число прочитанных OCR букв. Пороги, по которым это превращается в `matched`, `ambiguous` или
`not_found`, живут в `platform/api/src/recognizer/modelRecognizer.ts` и переопределяются
переменными `MODEL_*` — менять продуктовое поведение можно без пересборки образа с моделью.

Исключение — `POST /v1/eval/predict` на самом распознавателе: контракт скрипта организатора
требует один плоский ответ, и решать там некому.

## 1. Нормализация фото

Три места, каждое со своей задачей.

**Клиент** (`web/lib/prepareLabelPhoto.ts`): кадр ужимается до
`RECOMMENDED_MAX_IMAGE_SIDE_PX` = 1600 по длинной стороне и перекодируется в JPEG. Экономит
трафик и время загрузки, качество распознавания при этом не страдает. Бот берёт из размеров
Telegram наибольший, не длиннее 1600.

**API** (`api/src/image/inspectImage.ts`): формат определяется **по сигнатуре файла**, а не по
имени и не по заголовку. JPEG, PNG, WebP до 10 МБ, короткая сторона от 200 px. HEIC узнаётся
по бренду в `ftyp` и отклоняется с подсказкой сконвертировать — иначе пользователь iPhone
получил бы невнятную ошибку.

**Распознаватель** — здесь нормализация даёт основной прирост точности:

- **локатор бутылки** (`ml/locate.py`): Faster R-CNN MobileNetV3 на COCO, класс `bottle`.
  Из найденных рамок берётся самая центральная, а рамки, чей центр дальше 20% ширины от
  середины кадра, отбрасываются — это соседи по полке. Без отсева сосед выбирался в 12.8%
  кадров; отсев дал top-1 83.3% → 88.2% при потолке 90.0% с идеальной рамкой;
- **виды** (`ml/views.py`): один эмбеддинг плохо переживает разницу масштабов — крупный план
  этикетки против рендера всей бутылки. Поэтому из запроса режутся четыре вида (рамка бутылки,
  её нижняя часть с этикеткой, центр кадра, кадр целиком), из референса — два (бутылка и
  нижние 62%);
- для OCR берётся кроп по рамке бутылки: на полноразмерном фото текст читается, на кадре
  целиком — нет.

## 2. Извлечение признаков

**Визуальный сигнал.** SigLIP2 ViT-B/16 @256, дообученная на синтетике каталога. Выбор
энкодера мерялся (`ml/bench_zeroshot.py`): zero-shot SigLIP2 даёт 64.9% top-1 против 50.7% у
DINOv2 ViT-S/14 и 39.4% у CLIP ViT-B/16 — она фактически читает этикетку. Дообучение: последние
4 блока + attention-pool (35.4 млн параметров), CosFace по 2096 классам, прототипы стартуют с
zero-shot эмбеддингов. Обучающие кадры целиком синтетические (`ml/synth.py`): вырезанная
бутылка на фоне из не-каталожных фото, соседи по бокам, цилиндрическое затенение, блик,
перспектива, ценник, планка полки, баланс белого, шум, смаз, JPEG. Фоны делятся по хэшу имени,
чтобы eval-фоны не встречались на обучении.

Сходство запроса и референса = максимум по 8 парам видов.

**Текстовый сигнал.** PaddleOCR PP-OCRv5 (`ocr/paddle_worker.py`) по кропу бутылки. На
синтетике текст почти бесполезен — рендеры мелкие, медиана 336 px по ширине. На реальных фото
3024×4032 он читается хорошо и разбивает визуальные ничьи: Belmas «Pn» и «Vi» дают одинаковое
визуальное сходство, выбирает текст.

**Как это исполняется.** Две модели — два постоянных Python-воркера с протоколом «JSON по
строке» (`ml/worker.py`, `ocr/paddle_worker.py`), оркестрация на Node (`scripts/lib/recognizer.mjs`).
Окружений тоже два: torch и paddle тянут несовместимые numpy. Упавший или зависший воркер
перезапускается сам с паузой 1 → 30 с; на это время `/health` отвечает 503, а API —
`RECOGNIZER_UNAVAILABLE`.

## 3. Поиск по каталогу

```
визуальный топ-20  ─┐
                    ├─► fusion.mjs (условный логит) ─► slug + p
текстовый топ-5    ─┘
```

**Визуальный поиск** — косинус по индексу 2096 референсов
(`artifacts/model/index/*.npz`), полным перебором в памяти распознавателя. `pgvector` на
сервере не установлен, но при такой размерности перебор и не проигрывает: HNSW окупается на
других порядках.

**Текстовый поиск** (`scripts/lib/matcher.mjs`, `fuzzy.mjs`) — трёхступенчатый, потому что
название вина не идентификатор: «Рислинг» — это 37 разных вин. Первичный сигнал винодельня:

1. OCR-строка → винодельня: триграммы по `manufacturers.name_norm` и `slug_norm`, то есть
   кириллица и латиница сразу. Сужает 2041 → в среднем 15;
2. вино внутри портфеля (медиана 8, но `Фанагория` — 101);
3. цвет и сладость разводят остаток — 69 коллизий вида «производитель + название», оба слова
   напечатаны на этикетке.

Канонизация текста — `public.norm_label()` в базе и её зеркало в JS; равенство двух реализаций
проверяет `npm run check:norm-parity`.

**Слияние** (`scripts/lib/fusion.mjs`) — условный логит, веса лежат в
`artifacts/model/recognizer.json` и обучены на отложенных кадрах. Отдельная калибровка нужна
потому, что softmax-уверенность относительна: на чужом вине она бывает высокой (0.58), а
абсолютное визуальное сходство — нет (0.305 против минимум 0.576 у правильных ответов). Именно
поэтому отказ «вина нет в каталоге» строится на `visualMax`, а не на `confidence`.

Тот же код отвечает в сервисе и в офлайн-оценке `scripts/eval-recognizer.mjs` — метрики
меряются на том, что поедет в прод.

## 4. Выдача карточки

API складывает сигналы в контракт:

| Условие | Ответ |
|---|---|
| уверенность лидера ≥ 0.8 | `matched` + карточка + альтернативы |
| ниже порога | `ambiguous` + карточка + 3 альтернативы |
| `visualMax` < 0.4, OCR прочитал ≤ 3 букв | `not_found`, `reason: unreadable` — переснять |
| `visualMax` < 0.4, текст есть | `not_found`, `reason: not_in_catalog` |

Карточки — из Postgres, тем же `SELECT`, что выгрузил мок-каталог (`CatalogWineRow` →
`wineFromCatalogRow`). Каталог грузится в память при старте и обновляется раз в
`CATALOG_REFRESH_MS`: обрыв базы после старта ответы не ломает. Слаги, которых нет в каталоге
сайта (модель обучена на выгрузке, где их больше), в ответ не попадают.

«Не нашли» — это `200`, а не ошибка запроса. Ошибки приходят отдельной формой
`{ error: { code, message, requestId } }`, `message` по-русски и показывается пользователю.

Ответ распознавателя API проверяет схемой ещё раз: кривой ответ станет `500` с записью
`recognizer_contract_violation` в логе и не дойдёт до клиентов.

**Контракт — единственный источник правды** (`platform/contract`). Из zod-схем генерируется
`openapi.json`, тест падает, если файл отстал. TypeScript-клиенты берут `createWinvinoClient`,
остальные — кодогенерацию по OpenAPI. Правила совместимости: новые поля и коды ошибок
добавляются без смены версии (клиент игнорирует незнакомое), удаление поля или новый `status` —
только в `/v2`.

Новая реализация распознавания подключается типом `Recognizer` + веткой в `createRecognizer` —
контракт и клиенты при этом не меняются. Так и живёт `mock`: детерминированная заглушка по
sha256 фото, на ней делается весь интерфейс без базы и без GPU.

## 5. Функция после поиска

**Не реализована.** Пятый слой пайплайна — то, что удерживает пользователя после успешного
поиска (цифровой сомелье, подбор аналогов из других виноделен) — сейчас отсутствует, и `web`
показывает только карточку.

Место подключения готово с обеих сторон: у API уже есть каталог в памяти, а у распознавателя —
индекс эмбеддингов, по которому считается сходство между **винами**, а не только между фото и
вином. Подбор аналогов — это тот же индекс с другим запросом, отдельная модель не нужна.
Он же закрывает вторую половину требования «вина нет в каталоге»: вместо голого `not_found`
показать ближайшие по этикетке и по профилю позиции.

## Данные

**Каталог** живёт в Postgres (`migrations/`, [docs/DATABASE.md](docs/DATABASE.md)), зеркалится
с открытого API vino-svoe.ru командой `npm run catalog:sync`. Расширения `pg_trgm`, `unaccent`,
`fuzzystrmatch` включены в схему `extensions`, а не в `public`, чтобы не мешать дампам.

**Артефакты модели** (`artifacts/`) — чекпойнт, индекс референсов, `catalog.jsonl` для
OCR-матчера и `bundle.json` с sha256 каждого файла. Они лежат в git и запекаются в образ
распознавателя: в рантайме сервис в интернет не ходит, а версия модели едет одним коммитом с
кодом. Цена — ~355 МБ в истории на каждую версию модели; запасной путь (бандл по URL с
проверкой sha256) описан в [docs/DEPLOY.md](docs/DEPLOY.md) §10.

**Контур дообучения.** `SCAN_ARCHIVE=on` заставляет API сохранять каждое распознавание: фото в
том `scans`, строку в `label_scans` с `source='production'`. Эталон проставляется потом руками в
разделе `/admin` — очередь неразмеченных сканов с тремя действиями («верно», «на самом деле
это», «нет в каталоге»). Запись идёт мимо ответа и свои сбои гасит в лог: ни переполненный
диск, ни лежащая база не превращаются в ошибку пользователю. Раздел включается одной
переменной `ADMIN_PASSWORD`; не задана — роутов `/v1/admin/*` не существует.

Обучающих данных в репозитории нет — см. «Ограничения» в [README.md](README.md).

## Почему так

| Решение | Причина |
|---|---|
| Решение о `matched`/`not_found` в API, а не в распознавателе | пороги — продуктовое поведение, меняются без пересборки образа с моделью |
| Два Python-окружения | torch и paddle требуют несовместимых numpy |
| Постоянные воркеры вместо запуска процесса на кадр | загрузка моделей — секунды, кадр — доли секунды |
| Индекс в памяти, а не pgvector | 2096 референсов; полный перебор дешевле накладных расходов, и `pgvector` на сервере всё равно нет |
| Артефакты в git | деплой не зависит от внешнего хранилища, модель и код версионируются вместе |
| Один и тот же код в сервисе и в офлайн-оценке | метрики меряются на том, что поедет в прод |
| Mock-распознаватель в API | интерфейс разрабатывается без GPU и без базы |
