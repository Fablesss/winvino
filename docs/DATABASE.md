# База данных winvino

Postgres 18.6. Зеркало каталога [vino-svoe.ru](https://vino-svoe.ru/wines) плюс таблицы
под сканер этикеток.

## Инвариант

Схема и данные меняются **только закоммиченным файлом-миграцией**. Ни руками в клиенте,
ни разовым скриптом. Применение:

```
npm run db:migrate     # применить недостающие
npm run db:status       # показать, что ожидает применения
npm run catalog:sync    # пересинхронизировать каталог из API (идемпотентно)
```

Применённые миграции и их sha256 лежат в `public.schema_migrations`. Раннер откажется
работать, если файл уже применённой миграции изменился — правка делается новой миграцией.

## Имена миграций

```
<timestamp UTC>_<TASK>_<feature>_<action>.sql
```

Префиксы `feature` этого проекта (список экосистемы Zerocoder здесь не применяется):

| Префикс | Модуль |
|---|---|
| `system_` | Расширения, общие функции, триггеры |
| `catalog_` | Зеркало каталога: вина, винодельни, справочники |
| `scanner_` | Сканер этикеток: сканы, OCR, метрики матчера |

## Расширения

Включены в схему `extensions` (не в `public`, чтобы не мешать дампам):
`pg_trgm`, `unaccent`, `fuzzystrmatch`. `search_path` выставлен **на базу**, а не на роль —
роль `postgres` общая для всех 17 баз кластера, `ALTER ROLE` протёк бы в остальные.

**`pgvector` не установлен на сервере.** `pg_available_extensions` его не содержит,
поставить из строки подключения нельзя — нужен root на хосте (`apt install
postgresql-18-pgvector` либо образ `pgvector/pgvector:pg18`). До тех пор эмбеддинги в
`wine_photos` лежат как `real[]`. Переход, когда пакет появится:

```sql
ALTER TABLE wine_photos
  ALTER COLUMN embedding_full  TYPE extensions.vector(512) USING embedding_full::extensions.vector(512),
  ALTER COLUMN embedding_label TYPE extensions.vector(512) USING embedding_label::extensions.vector(512);
```

Индексы (HNSW/IVFFlat) при 2041 строке не нужны: полный перебор дешевле накладных расходов.

## Матчер: как устроен поиск

Название вина **не идентификатор** — «Рислинг» это 37 разных вин. Первичный сигнал —
винодельня, поэтому поиск двухступенчатый:

1. **Ступень A** — OCR-строка → винодельня. Триграммы по `manufacturers.name_norm` и
   `slug_norm`, то есть кириллица и латиница одновременно. Сужает 2041 → в среднем 15.
2. **Ступень B** — вино внутри портфеля. Медиана 8 вин на винодельню, но распределение
   перекошено: `Фанагория` 101, `Кубань-Вино` 97, `Мысхако` 92.
3. **Ступень C** — `wine_color` и `sweetness` разводят остаток (69 коллизий вида
   «производитель + название»); оба слова напечатаны на этикетке.

`public.norm_label()` канонизирует текст: регистр, `ё→е`, удаление `ъ`/`ь`
(«Ведерниковъ» → `ведерников`), пунктуация в пробелы. Латиница сохраняется.

## Особенности источника, на которые натыкались

- **`perPage` максимум 30.** 31 и больше — HTTP 400. Полный каталог = 69 запросов.
- **`publicRating` дробный.** В списке выглядит целым (`2`, `4`), в деталях приходит
  `2.25`. Поэтому `numeric(3,2)`, а не `smallint`.
- **Поле `color` в API — не цвет вина,** а описание оттенка («Соломенный с золотистыми
  переливами»). В схеме называется `hue`. Цвет вина берётся из `category`.
- **Год урожая есть только у 112 названий из 2041.** Как фильтр непригоден, только
  слабый тайбрейкер. Отдельного поля в API нет вовсе.
- **У 3 виноделен API не отдаёт слаг.** `Поместье Голубицкое`, `Mancopia`,
  `Wein und Wasser` приходят в `/wines/{slug}` как `{name}` без `slug`, и в
  `/manufacturers` отсутствуют. Слаг для них генерируется локально (`slugify()` в
  `scripts/sync-catalog.mjs`), иначе их 9 вин остаются без винодельни.
- **`Поместье Голубицкое` и `Golubitskoe Estate` — вероятно одна винодельня** под двумя
  названиями. В базе это две строки. Merge алиасов — отдельная задача.
- **`altText` у картинок ненадёжен:** расходится с `title` у 987 вин из 2041, местами
  просто неверен. Как источник названия не использовать.
- **Прямой путь к картинке отдаёт 404.** Только через ресайзер:
  `https://api.vino-svoe.ru/v1/img/str-api/{w}/{h}/resize/uploads/xxx.webp`.

## Eval-набор

`label_scans` — измерительный прибор матчера: фото, OCR, эталонный slug, предсказание,
`truth_rank` (1 = top-1, NULL = не попал в выдачу) и `candidates` с топом кандидатов.
`truth_absent = true` означает «вина нет в каталоге» — такие кадры обязательны, иначе
метрика не увидит уверенного вранья на импортном вине.

Сводка: `SELECT * FROM label_scan_accuracy;` — top-1, top-5 и false positives по версиям
матчера, только по `source = 'eval_set'`.

## Self-test на рендерах каталога

`npm run selftest` прогоняет OCR по всем 2041 рендеру и матчит обратно в каталог,
`npm run selftest:report` считает отчёт. Пишет в `label_scans` с
`source = 'catalog_selftest'`, поэтому `label_scan_accuracy` остаётся чистой.

**Это потолок, а не ожидаемая точность.** Замкнутый контур: запрос и референс происходят
из одного изображения. Не покрывает угол, блики, освещение, частично закрытую этикетку и
случай «вина нет в каталоге».

Результат на 2041 кадре (tesseract.js rus+eng, `idf-mass-translit-v3`):

| Метрика | Значение |
|---|---|
| top-1 | 17.0% |
| top-5 | 32.2% |
| top-20 | 47.1% |
| ступень A: винодельня в top-1 | 29.5% |
| ступень B при верной винодельне | 34.4% |
| эталонная винодельня прочиталась (score ≥ 0.5) | 20.2% |
| эталонное название прочиталось (score ≥ 0.5) | 27.7% |

Вывод: **упор в OCR, а не в матчере.** Идентифицирующий текст вообще читается лишь в
20–28% кадров, при этом ступень A вытягивает 29.5% — то есть матчер работает выше наивного
порога читаемости. Причины: в кадре вся бутылка (этикетка занимает треть), у tesseract нет
детектора текста на изображении, декоративная типографика этикеток. (Первоначально здесь
была названа и узкая ширина оригиналов — разбивка по ширине это опровергла, см. ниже.)

Проверенные и отвергнутые варианты:

- **Полоса с этикеткой вместо полного кадра** (`preprocess(buf, 'band')`) — хуже:
  top-5 18% против 33%. Фиксированная вертикальная полоса промахивается по этикетке на
  бутылках разной формы. Нужна настоящая детекция области этикетки.
- **Глагол `fit` вместо `resize`** для более крупной картинки — пустышка: `fit`
  апскейлит оригинал до запрошенного бокса, новой детализации нет, растут только байты.
  Настоящий предел — исходное разрешение в хранилище.

Дальнейшая подкрутка весов матчера на выходе tesseract будет подгонкой под шум OCR.
Следующий шаг — движок, рассчитанный на текст на фото, а не на страницы: см. PaddleOCR ниже.

## PaddleOCR PP-OCRv5

Tesseract — OCR для документов: у него нет детектора текста на изображении, и на рендере
бутылки он пытается читать стекло и фольгу как строки. PaddleOCR сначала находит рамки с
текстом, потом читает каждую. Модели: `PP-OCRv5_mobile_det` (4.7 МБ) и
`eslav_PP-OCRv5_mobile_rec` (14 МБ, русский/белорусский/украинский).

Конвейер — отдельное Python-окружение, Node остаётся для матчинга и базы:

```
npm run ocr:paddle:setup    # .venv-ocr на Python 3.12 из ocr/requirements.lock.txt
npm run ocr:paddle:pilot    # 20 кадров, прямое сравнение с tesseract на тех же картинках
npm run ocr:paddle:list     # список всех 2037 уникальных рендеров
npm run ocr:paddle:run      # распознавание в JSONL; при обрыве запустить снова — продолжит
npm run ocr:paddle:ingest   # матчинг и запись в label_scans рядом с tesseract
npm run selftest:rematch    # перематчить сохранённый OCR текущим матчером
npm run selftest:report     # отчёт по движкам + сравнение на общих кадрах
```

Перед повторным `ocr:paddle:run` убедиться, что прошлый процесс не жив: два процесса,
дописывающие один JSONL, перемешают строки.

### Ограничения окружения

- **`paddlepaddle` закреплён на 3.2.0.** В 3.3.x на CPU связка oneDNN + исполнитель PIR
  падает на каждом кадре (`ConvertPirAttribute2RuntimeAttribute not support`,
  PaddleOCR#18162). Без oneDNN работает, но в 4 раза медленнее: 2881 против 728 мс/кадр.
- **Только CPU.** GPU-сборка Paddle на Windows требует CUDA compute capability выше 7.5,
  у GTX 1050 Ti — 6.1.
- **Ускоренный режим (high-performance inference) — только Linux.** На Windows реальны
  «стандартные» тайминги из документации.
- Замер на i5-4440: ~0.73–0.8 с на кадр, пик памяти ~1 ГБ, инициализация ~7 с.
  Окружение занимает 824 МБ.

### Двойники букв

Распознаватель `eslav` на заглавных пишет русские слова латинскими и греческими
двойниками: «ABTOPCKOE MACCAHДPA … KOKYP» — это идеально прочитанное
«АВТОРСКОЕ МАССАНДРА … КОКУР», «PO3E» — «РОЗЕ» с цифрой, «5ΛΑΗ» — «БЛАН». Транслит этого
не ловит: латинская C выглядит как С, но транслит превращает С в «s». В матчере
(`idf-mass-translit-skeleton-v4`) добавлено третье пространство сравнения — по
начертанию (`skeleton()`), и греческие буквы сворачиваются до нормализации
(`foldGreek()`). На тех же закешированных OCR-результатах: «Кокур авторское» — эталон
с 904-го места на 2-е, «Розе авторское» — с 76-го на 1-е.

### Результаты

Пилот на 20 одинаковых кадрах, матчер v4:

| Движок | top-1 | top-5 |
|---|---|---|
| tesseract.js rus+eng | 25% | 50% |
| PaddleOCR PP-OCRv5 | 40% | 55% |

Tesseract на всех 2041 кадре после перематчинга v4: top-1 17.5% (было 17.0% на v3),
top-5 33.2%. Правки матчера сами по себе дали полпункта — двойники букв это болезнь
PaddleOCR, а не tesseract.

Полный прогон по всем 2041 кадру, оба движка через один матчер v4:

| Метрика | tesseract.js | PaddleOCR PP-OCRv5 |
|---|---|---|
| top-1 | 17.5% | **36.8%** |
| top-5 | 33.2% | **59.6%** |
| top-20 | 47.9% | 74.5% |
| медиана позиции эталона | 22 | **3** |
| ступень A: винодельня в top-1 | 30.1% | 54.6% |
| ступень B при верной винодельне | 35.0% | 51.3% |
| эталонная винодельня прочиталась | 20.3% | 39.7% |
| эталонное название прочиталось | 28.7% | 52.2% |
| пустой OCR | 1.0% | 0.3% |
| OCR, мс/кадр | ~3400* | ~850 |

\* tesseract мерился при 6 воркерах на 4 ядрах, цифра раздута конкуренцией за CPU.

Лицом к лицу на одних и тех же кадрах (top-1): верно только у PaddleOCR — 476 (23.3%),
только у tesseract — 82 (4.0%), у обоих — 276, мимо у обоих — 1207. Объединение движков
подняло бы top-1 лишь до 40.9%, то есть на 4 пункта против одного PaddleOCR. Держать
tesseract вторым движком не окупается.

Это по-прежнему **потолок на замкнутом контуре**, а не точность на живых фото. Главный
упор сдвинулся, но остался в OCR: винодельня читается в 40% кадров.

### Разрешение оригинала — не упор

`scripts/db-diagnose-by-width.mjs`, точность по ширине исходного рендера:

| Ширина | Кадров | PaddleOCR top-1 | PaddleOCR top-5 | Винодельня прочиталась | tesseract top-1 |
|---|---|---|---|---|---|
| < 250px | 264 | 40.9% | 62.9% | 47.7% | 17.8% |
| 250–349px | 816 | 37.9% | 61.0% | 42.9% | 17.6% |
| 350–599px | 506 | 34.0% | 55.9% | 25.3% | 18.8% |
| 600–999px | 151 | 41.7% | 63.6% | 37.7% | 13.9% |
| ≥ 1000px | 304 | 32.9% | 57.2% | 49.0% | 16.8% |

Зависимости «шире — точнее» нет ни у одного движка. **Это опровергает вывод из фазы
tesseract**, где узкие оригиналы (медиана ~335px) названы одной из причин провалов:
данные его не подтверждают, и апскейл не поможет. Оговорка: ширина оригинала — только
приближение к размеру этикетки, крупный кадр бывает в основном полями вокруг бутылки.

Оставшиеся промахи, судя по разбору отказов, дают другое: декоративные шрифты, винодельня
не напечатана крупно на лицевой этикетке, у одной винодельни несколько вин с одинаковым
сортом (ступень B — 51%), недосвёрнутые двойники букв.
